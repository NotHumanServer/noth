# 実装プラン: 擬似 Discord ハーネス fakecord

## 目的

本物の Discord につないでテストするのは手間がかかり、本番のサーバーログも増えます。そこで、127.0.0.1 で動く擬似 Discord を作り、CLI から GUI の操作(発言、チャンネルとスレッドの作成、slash、ボタン、リアクション)を再現します。AI エージェントがこれを使って、評価と改善を繰り返せるようにします。

## 決定事項

- Rust で自作し、同じリポジトリに `crates/noth-fakecord`(lib + バイナリ `fakecord`)として置きます。既存 OSS の fauxcord(Node.js、MIT、star 0、serenity 互換は README の主張のみ)は使いません。
- router(System One)と provider(OpenAI)は本物を使います。差し替えるのは Discord だけです。`NOTH_HOME` は本番と分けます(例: `~/.noth-dev`)。
- 並列実装には Orca のオーケストレーションを使い、OpenCode の `opencode/deepseek-v4.1-flash-free` を回します。GLM-5.3-Flash と比べた根拠は次のとおりです。
  - 速度は Artificial Analysis の実測で 176 tok/s 対 69 tok/s です。
  - ベンダー公表値は Terminal-Bench 2.1 が 90.6 対 84.3、DeepSWE が 74.2 対 63.4 です。ただし計測ハーネスが違います。
  - OpenCode の無料枠は zero-retention で学習に使われませんが、期間限定でレート制限は非公表です。

## 調査で分かった事実

### noth 側

- serenity 0.12.5 を使っています(features: client, gateway, model, http, cache, rustls_backend)。intents は `GUILDS | GUILD_MESSAGES | MESSAGE_CONTENT` です。
- 受けているイベントは ready、resume、cache_ready、channel_create/update/delete、category_delete、thread_create/update/delete、thread_list_sync、interaction_create(Command と Component)、message です。cache_ready があるので、GUILD_CREATE にチャンネル一覧を含める必要があります。
- serenity 経由の REST は次のとおりです。
  - `GET /users/@me`
  - `GET /oauth2/applications/@me`
  - `GET /guilds/{id}`
  - `GET /guilds/{id}/channels`
  - `GET /guilds/{id}/threads/active`
  - `GET /channels/{id}`
  - `GET /guilds/{id}/roles`
  - `GET /guilds/{id}/members/{uid}`
  - `POST /channels/{id}/messages`(allowed_mentions 空、message_reference、2000 字で分割)
  - `PATCH /channels/{id}/messages/{mid}`
  - `PUT /channels/{id}/messages/{mid}/reactions/{emoji}/@me`
  - `POST /channels/{id}/typing`
  - `GET /gateway`
- reqwest で直接叩いている REST が 2 か所あります。どちらも `https://discord.com/api/v10` がハードコードで、`with_base` はテスト専用です。
  - `crates/noth-channel-discord/src/command/api.rs`
    - `PUT /applications/{app}/guilds/{guild}/commands`
    - `POST /interactions/{id}/{token}/callback`
    - `PATCH /webhooks/{app}/{token}/messages/@original`
    - `POST /webhooks/{app}/{token}`
  - `crates/noth-tool-discord/src/api.rs`(GET のみ)
    - `GET /channels/{id}/messages?limit&before|after|around`
    - `GET /channels/{id}/messages/{mid}`
    - `GET /channels/{id}/messages/pins`(404 なら `/channels/{id}/pins`)
    - `GET /guilds/{id}/channels`
    - `GET /guilds/{id}`
    - `GET /guilds/{id}/roles`
    - `GET /guilds/{id}/members/{uid}`
    - `GET /channels/{id}`
- Components V2 は生 JSON で組んでいます。flags は 64(ephemeral)と `1<<15`(IS_COMPONENTS_V2)です。component type は 17、10、14、1、2 です。ボタンの custom_id は `noth:refresh:<command>` です。応答 type は 4、5、6 を使います。
- 既存のテストには、手書きの TCP サーバー(`command/tests.rs`、`tool-discord/src/tests.rs`)と、trait(`DiscordApi`、`InteractionApi`)の Fake があります。

### serenity と Discord の仕様

- `HttpBuilder::proxy(url)` は `https://discord.com` 部分を置き換えます。`/api/v10` は route 側に残るので、proxy には含めません。
- 重要: ratelimiter が有効だと proxy が無視され、本物の Discord に飛びます(v0.12.5 の `ratelimiting.rs` がリクエストを組み立てるときに None を渡しています)。必ず `ratelimiter_disabled(true)` と組み合わせます。
- Gateway URL は ClientBuilder が `GET /api/v10/gateway` の url を使い、`?v=10` を付けて接続します。取得に失敗すると `wss://gateway.discord.gg` に黙ってフォールバックします。そのため、擬似サーバーは `/gateway` を必ず実装し、漏れていないことを検証項目にします。
- `Client::builder` 内の Http は proxy を設定できません。`ClientBuilder::new_with_http` に proxy 付き Http を渡します。
- serenity は Identify で `compress: true` を送りますが、Text フレームで返せば問題ない見込みです。ws:// の平文接続は、ソース上は可能ですが未実測です。`resume_gateway_url` は使わず、保存した ws_url で再接続します。
- Gateway の流れは次のとおりです。op 10 Hello(heartbeat_interval)、op 2 Identify、op 0 READY(v, user, guilds, session_id, resume_gateway_url, application)、GUILD_CREATE の順です。ほかに op 1/11 heartbeat、op 6 Resume、op 7 Reconnect、op 9 Invalid Session があります。
- interaction の初回応答は `POST /interactions/{id}/{token}/callback`(既定 204、3 秒以内)です。followup は `POST /webhooks/{app}/{token}`、原応答の編集は `PATCH .../messages/@original` です。

## 構成

### サーバー

`fakecord serve --port 3900` で 127.0.0.1 のみで待ち受けます。状態はメモリに持ち、JSON スナップショットの保存と読み込みに対応します。

- Gateway: Hello、Identify、heartbeat、READY、GUILD_CREATE(チャンネル込み)、Resume に対応します。MESSAGE_CREATE、MESSAGE_UPDATE、チャンネルとスレッドの増減、INTERACTION_CREATE を配信します。
- REST: 上記の全エンドポイントと `/gateway`、`/gateway/bot` を実装します。
- 操作用 API: `/_fake/...` です。CLI がこれを叩きます。

### CLI

`--json` で機械可読な出力を返します。

- `fakecord send --channel general --as kurazu "のす、おはよ"`(返信、メンション、Bot の発言にも対応)
- `fakecord channel create` / `category create` / `thread create` / `delete` / `rename`
- `fakecord slash noth context --as kurazu`、`fakecord click <custom_id>`、`fakecord react`
- `fakecord log --channel general`
- `fakecord wait-reply --timeout 60`(Bot の投稿、編集、リアクションを待つ)
- `fakecord user add`(allowed_users 役と master 役)

### noth 側

`[channel.discord] api_base = "http://127.0.0.1:3900"` を足し、設定時は 3 か所すべてをそこへ向けます。

- serenity: `proxy` + `ratelimiter_disabled(true)` + `new_with_http`
- `command/api.rs` と tool-discord: ベース URL を置き換える

未設定なら従来どおり本物の Discord に向きます。

### 起動

`scripts/fakecord-up.sh` で fakecord と、別 `NOTH_HOME` の noth をまとめて起動します。

## 進め方

1. **土台**(Sonnet の implementer 1 人): crate の雛形、状態モデルの型、ルーターの空関数、操作用 API の JSON 仕様、CLI のコマンド定義を作り、`cargo check` が通る状態にします。並列作業はこれを契約にします。
2. **超並列**(Orca + OpenCode deepseek-v4.1-flash-free を 9 体): 担当ファイルを重ねません。
   - Gateway
   - REST(ユーザー・アプリ・gateway)
   - REST(guild・channels・roles・members・threads)
   - REST(メッセージ・typing・リアクション・pins)
   - interaction・webhook・コマンド登録
   - 操作用 API
   - CLI
   - noth の api_base
   - 互換テスト(fakecord が返す JSON を serenity の型で deserialize できるか)と起動スクリプト
3. **統合**(Sonnet): build、test、clippy を通します。cargo の後には必ず `scripts/prune-target.sh` を実行します。
4. **レビュー**(Sonnet の reviewer を観点ごとに並列): 特に、本物の Discord への漏れがないかを見ます。
5. **実測**(tester): 起動、発言、noth の返信、`/noth context`、スレッドの作成を確かめます。
6. コミットはユーザーの指示のあとで、トピックごとに入れます。

## 検証項目

- fakecord 起動中に noth が discord.com / gateway.discord.gg へ一切通信しないこと(ログ、または接続先を観測して確かめます)
- READY と GUILD_CREATE を受けて「接続済み」になること
- 発言に対する判定、返信、リアクション、typing が fakecord 側に記録されること
- `/noth context`、`/noth ignore add|list|remove`、更新ボタンが動くこと
- チャンネルとスレッドの作成・削除で、除外の展開が追従すること
